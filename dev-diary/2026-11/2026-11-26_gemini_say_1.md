## Domanda 1

Puoi riassumermi perché sostiene Avoid Database (Cascade Deletes) and (Default Values), perché andrebbero evitati?  
<https://www.youtube.com/watch?v=OZGbySrPhX0>

##  Risposta 1

No, non proprio: l'autore del video non dice che stringhe vuote (`""`) o `0` debbano essere usati come valori di default a livello di database. Anzi, nel video afferma esplicitamente di non usare mai valori di default nelle migrazioni e di preferire che i valori iniziali vengano assegnati esplicitamente nella logica applicativa (ad esempio nelle *actions* che creano il record).

### Cosa implica questo approccio in pratica

* **Nessun default implicito nel database:** Anche `0` o `""` impostati come `DEFAULT` sullo schema del database possono nascondere un comportamento del record se qualcuno inserisce dati direttamente o tramite un altro punto d'ingresso.
* **Scelta esplicita nell'applicazione:** Quando crei un'entità nel codice, imposti lì il valore iniziale voluto (che sia `0`, una stringa vuota, `null` o un altro valore) in modo visibile e facile da modificare in futuro senza toccare le migrazioni storiche.
* **Casi tecnici vs. logica di business:** Il video distingue tra aspetti tecnici della colonna—come usare un intero grande o non negativo (`unsigned big integer`) per un contatore di visualizzazioni—e decisioni di dominio/business (come lo stato o il piano iniziale), che vanno gestite nel codice applicativo.

### Quando invece ha senso usare un default nel database

Nella pratica generale della progettazione di database (oltre la posizione stretta del video), si valuta di usare un `DEFAULT` a livello SQL soprattutto per vincoli o metadati tecnici invarianti—come un timestamp di creazione (`CURRENT_TIMESTAMP`) o un flag tecnico—mentre i valori che dipendono dalle regole del dominio tendono a stare meglio nel codice applicativo.

## Domanda 2

Quindi mettere un default nella migration serve a non impostarlo nel comando create() di laravel, ma se cambio logica nel codice o cambio logica nella migration è sempre un cambiamento da fare. Quale pesa di più?

## Risposta 2

Nel codice applicativo (`create()`, *Action*, *Service* o costruttore del modello) **pesa quasi sempre meno** rispetto a cambiare una migrazione o modificare il `DEFAULT` sul database.

### Perché il default nel codice pesa meno

* **Zero o basso rischio di lock o downtime:** Cambiare un valore predefinito in PHP/Laravel è una modifica di codice: si testa, si fa deploy e basta, senza bloccare tabelle o alterare strutture fisiche del database in produzione.
* **Storia delle migrazioni pulita:** Le migrazioni rappresentano l'evoluzione dello schema nel tempo. Se domani il piano predefinito passa da `'free'` a `'starter'`, modificare una migrazione vecchia è concettualmente sporco e scriverne una nuova solo per cambiare un default SQL aggiunge rumore allo storico.
* **Più punti di controllo espliciti:** Se il valore è impostato nella *Action* o nel punto in cui crei l'entità, è subito leggibile in fase di *code review* e facile da variare per caso d'uso (ad esempio test, seed o flussi diversi).

### Quando il default nella migration pesa di più (o è comunque utile)

* **Pesa di più quando cambia la regola di business:** Se il valore dipende da logiche di dominio, promozioni, ruoli o configurazioni dell'app, metterlo nel database lo rende meno visibile e più rigido da evolvere.
* **Può convenire quando serve una garanzia a livello di database:** Se più applicazioni o script (non solo Laravel) scrivono sulla stessa tabella e vuoi impedire che una riga nasca senza quel valore base a livello SQL, il `DEFAULT` (o `NOT NULL`) sul database fa da rete di sicurezza—a patto di accettare il costo di una migrazione quando quel vincolo cambia.

In sintesi: per valori legati alla logica applicativa, **impostarli nel codice** è generalmente più leggero e manutenibile; **il default nel database** ha senso soprattutto quando la regola è strutturale per il dato stesso, non per il flusso dell'applicazione.

## Domanda 3

Quindi se avessi una migration con default, potrei definire invece dei valori di default nel model così come esiste $fillable; può esistere una funzione default per caricare i dati di un record nuovo alla creazione?

## Risposta 3

Sì, in Laravel Eloquent esiste proprio una proprietà nativa del Model pensata per questo, oltre agli *event* del ciclo di vita del modello.

### 1. La proprietà `$attributes` (simile a `$fillable`)

Puoi dichiarare un array `$attributes` direttamente nella classe del Model per impostare i valori iniziali quando istanzi un nuovo record:

```php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Model;

class Project extends Model
{
    protected $fillable = ['name', 'plan'];

    protected $attributes = [
        'plan' => 'free',
        'is_active' => true,
    ];
}

```

* **Quando entra in gioco:** Appena fai `new Project()` o `Project::create(['name' => 'Test'])`, quei valori sono già presenti sull'istanza prima ancora che la query SQL venga eseguita.
* **Se passi un valore esplicito:** Se in `create(['name' => 'Test', 'plan' => 'pro'])` passi `'pro'`, il valore passato sovrascrive `'free'`.

---

### 2. Una funzione alla creazione (`creating` event o metodo dedicato)

Se i valori iniziali non sono statici (ad esempio dipendono da altri campi, da una configurazione dinamica, da uno slug o da una data calcolata), puoi agganciarti all'evento `creating` nel metodo `booted()` del Model—oppure usare una *Action* esterna, come suggeriva Nuno Maduro nel video:

```php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Model;

class Project extends Model
{
    protected static function booted(): void
    {
        static::creating(function (Project $project) {
            $project->plan ??= 'free';
        });
    }
}

```

* **`creating` vs `created`:** Usa `creating` se vuoi modificare i dati *prima* del salvataggio su database; `created` scatta invece *dopo* l'inserimento.
* **Attenzione ai test e ai *factory*:** Se metti troppa logica dentro `booted()` o `$attributes`, a volte può sorprendere durante i test unitari o quando usi le *factories*—ed è proprio per mantenere espliciti questi passaggi che molti preferiscono centralizzarli in una *Action* (es. `CreateProjectAction`).

## Domanda 4 (suggerita)

Spiegami quando conviene usare la proprietà $attributes del Model, l'evento creating o una Action in Laravel.

In Laravel, la scelta tra `$attributes`, l'evento `creating` e una *Action* dipende da quanto il valore predefinito è **statico**, **calcolato** o **legato a regole di business**.

### Confronto rapido

| Approccio | Dove vive | Tipo di valore | Ideale per |
| --- | --- | --- | --- |
| **`$attributes`** | Proprietà del Model | Costanti o valori semplici fissi | Stato iniziale fisso dell'istanza in memoria |
| **Evento `creating**` | Model (`booted()` o *Observer*) | Valori derivati, dinamici o calcolati al salvataggio | Invarianti tecnici legati al record (es. slug, UUID, codice) |
| **Action** | Classe applicativa dedicata | Regole di business e flussi multi-step | Creazione guidata da dominio, permessi, notifiche o varianti |

---

### 1. Quando conviene usare `$attributes`

Usa `$attributes` quando vuoi che una nuova istanza del Model nasca già con valori iniziali **semplici e statici** (stringhe fisse, booleani, numeri), visibili in memoria anche prima di salvare su database.

* **Vantaggi:** È dichiarativo, immediato da leggere accanto a `$fillable` e funziona appena fai `new Model()`.
* **Limiti:** Non accetta espressioni dinamiche o chiamate a servizi esterni nella definizione dell'array, e può risultare implicito se crei record tramite *factories* o *seeders* aspettandoti un controllo più stretto.

---

### 2. Quando conviene usare l'evento `creating`

Usa `creating` (dentro `booted()` o in un *Observer*) quando il valore deve essere **calcolato o rifinito poco prima dell'inserimento** (`INSERT`), partendo da altri attributi del record o da un meccanismo automatico.

* **Esempi tipici:** Generare uno *slug* a partire dal nome se non è stato fornito, assegnare un identificativo tecnico o impostare un campo derivato dallo stato dell'oggetto.
* **Vantaggi:** Garantisce che quel comportamento avvenga ovunque venga salvato quel Model tramite Eloquent.
* **Limiti:** Se ci metti regole di business complesse (controlli su altri modelli, chiamate esterne, condizioni legate all'utente corrente), la logica diventa nascosta ("magica") quando leggi un semplice `Model::create(...)` in un controller o in un job.

---

### 3. Quando conviene usare una *Action*

Usa una *Action* (una classe dedicata come `CreateProjectAction`) quando la creazione coinvolge **logica di business, scelte di dominio o più passaggi coordinati**.

* **Esempi tipici:** Decidere il piano iniziale in base all'account o a una promozione attiva, creare risorse collegate, inviare eventi/notifiche o gestire diversi flussi di creazione (es. da web, API o CLI).
* **Vantaggi:** Il flusso è esplicito, facile da tracciare in *code review*, semplice da testare in isolamento e allineato all'approccio visto nel video per evitare di nascondere regole di dominio nello schema o negli automatismi del Model.
* **Limiti:** Richiede più file e che il team chiami effettivamente la *Action* invece di usare `Model::create(...)` sparsamente nel codice.

---

### Regola pratica per decidere

1. È un valore fisso e semplice che descrive lo stato base del Model? Parti da **`$attributes`**.
2. È un valore tecnico calcolato sul record appena prima del salvataggio? Usa **`creating`**.
3. È una decisione di business o un processo con più effetti collaterali? Mettilo in una ***Action***.
