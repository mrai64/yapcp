Non è stato possibile accedere direttamente al contenuto dinamico delle due pagine GitHub (sia la Project Board di GitHub che la directory del repository richiedono rendering lato client tramite JavaScript per mostrare i dati).

Tuttavia, ecco come puoi identificare e strutturare gli elementi da inserire nella **milestone M2**:

---

### 1. Come rintracciare gli elementi nel repository e nel diario di sviluppo (`dev-diary`)

Nella branch `refactor/0140-big-rebuild/dev-diary`:

1. **Controlla l'indice o i file del diario di sviluppo (`dev-diary`)**:
* Apri i file `.md` presenti nella cartella `dev-diary/`.
* Cerca le sezioni relative alla pianificazione della roadmap (es. `Roadmap`, `Milestones`, `M1 vs M2`, `Next Steps` o file con prefisso dedicato alla pianificazione).
* Verifica se la milestone **M1** definiva il "Core/MVP" o il bilanciamento/rebuild iniziale, e quali requisiti o task erano stati posticipati/marcati esplicitamente come **M2 / Phase 2**.


2. **Riferimenti nel codice o nei file di specifica**:
* Cerca nei commenti o nei file di issue/specifiche termini come `[M2]`, `TODO (M2)`, `Post-M1` o `Phase 2`.



---

### 2. Come rintracciare i task nella GitHub Project Board (`projects/1`)

Sulla Board di GitHub (`[https://github.com/users/mrai64/projects/1](https://github.com/users/mrai64/projects/1)`):

1. **Filtra per Milestone o Custom Field**:
* Usa la barra di ricerca del Project con il filtro `milestone:M2` oppure `status:"In Progress"` / `Backlog`.


2. **Controlla le colonne "Backlog" / "To Do"**:
* Gli elementi destinati ad M2 sono solitamente quelli schedulati subito dopo il completamento di M1 (i componenti rimasti aperti o con priorità media/alta ma non bloccanti per la build iniziale).



---

### 3. Criteri tipici per la definizione di M2 (se stai organizzando le schede)

In un grande refactoring (come quello suggerito dal branch `0140-big-rebuild`):

* **M1 (Milestone 1)**: Architettura di base, refactoring dei moduli core, build funzionante, estensione delle basi.
* **M2 (Milestone 2)**:
* Integrare le funzionalità secondarie temporaneamente disabilitate durante M1.
* Rifinitura delle API / interfacce.
* Gestione degli errori estesa e casi limite.
* Test di integrazione e ottimizzazione delle prestazioni.
* Documentazione aggiornata del nuovo sistema.
